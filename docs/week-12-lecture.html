Evaluating an AI system

Modern AI Systems · Lecture 12

Week 12 — How do we know that a change made the system better, and what does one answer cost?

1

Main idea

A change to an AI system is often judged by reading an answer or two.

  • The same question can be answered differently on the next run
  • A change that repairs one question can break another

Two measures decide instead:

  • a test set: whether the system answers correctly
  • the cost of an answer: model calls, tokens and time
2

One answer is not evidence

ChangeOften judged by
chunk sizethe passages returned for a few questions
retrieverthe answers to a few questions
instruction, memory positionan answer or two
a guard against injectionone run of each attack

"The system works" and "this change helped" are claims about many questions, each answered more than once: a model's answer varies between runs, even at temperature 0. Without a test set, a result is an impression.

3

What a test set holds

Questions representative of the intended user, each with an expected answer or the properties a correct answer must have.

KindExampleExpected
ordinaryWhat distance does Chroma use by default?squared Euclidean, with a source
needs a toolHow many hryvnias is 250 euros at today's NBU rate?exchange_rate, then 250 × the rate
follow-upHow do we change it?set hnsw:space to cosine
to be declinedWhat is the penalty for submitting a lab late?not stated in the course materials
an attackan ordinary question, with a planted post in the sourcesno address in the answer
4

Rules for a test set

  • Fixed before the change it is to judge, so that it cannot be fitted to the result
  • Covers every kind of interaction the project offers, not only those that work
  • Grows: extended with every failure found or every new method introduced
5

Evaluation by stage

A wrong answer has a location, and the location decides what the next change must be.

StageFails whenChecked against
retrievalthe passage holding the answer is not foundthe passages that hold the answer
answera passage is present but not used, or exceededthe expected answer, and the answer's own sources
toolsa wrong tool, a wrong argument, or no callthe tool calls the question requires
memorya stale or false fact is recalledthe facts that should, and should not, be stored

A correct answer from the wrong passages, and a wrong answer from the right passages, call for different changes.

6

Retrieval metrics and answer metrics

MeasureQuestion it answers
hit at kIs a passage holding the answer among the k retrieved?
correctDoes the answer agree with the expected answer?
groundedIs every claim in the answer supported by the sources it was given?
7

Three judges

JudgeSuited toLimitation
a rule in codeanswers of fixed form: a number, a name, a link present, a tool calledcannot judge an open answer
a personopen answers: verdicts such as correct, partly, wrong, silentslow; one person's standard
a modelopen answers, at the scale of the test setbiased; costs requests
8

Checking the judge

Before its scores are used:

  1. Judge a sample of the answers yourself
  2. Let the model judge the same sample
  3. Compare the verdicts, question by question
  4. Where they disagree, revise the rubric, or keep those questions for a person

The agreement on the sample is reported with the results: a score from an unchecked judge is another impression.

9

Regression testing

After every change, the whole set is run again and compared question by question. An illustration, not a result:

question    before     after
Q1          correct    correct
Q2          wrong      correct      repaired
Q3          correct    wrong        broken
total       2 of 3     2 of 3       the total hides both

Every failure found joins the set, known attacks among them. A question whose answer varies is run several times, and the model that answered is recorded with each run.

10

The cost of one answer

cost   =  model calls  ×  tokens of each call

          input    instruction · tool definitions · memory · history · sources · tool results
          output   tool calls · the answer · reasoning tokens

time   =  the calls, one after another  +  each tool's own time
price  =  input tokens × input price  +  output tokens × output price      (paid tier)

Reasoning tokens are "considered output tokens and charged accordingly", whether or not they are shown.

Source: OpenRouter, Reasoning Tokens

11

Every design complication traded against cost and performance

DecisionEffect on cost
retrieval as a fixed stepone call; the sources in every prompt
retrieval as a toola call per search, and a call to answer
historyevery turn sends all earlier turns again; a summary caps it, for one call
memory extracted by the applicationone more call after every turn
tools, local or from MCPevery definition is sent with every call
a call limitcaps the worst case; a stopped run has spent its calls and gives no answer

For each question of the test set, record the calls, the tokens and the time; report the typical answer and the worst, and the component that accounts for most of the cost.

12

Lowering the cost without changing the design

  • Prompt caching, where the provider supports it: a repeated beginning of the prompt, such as the instruction and the tool definitions, is charged at a fraction of the input price
  • A different model for each step: a smaller one for routing or extraction, a stronger one where the step needs it, such as writing a query
  • Fewer tokens per call: fewer passages, a summarised history, only the tools the question can use
  • Limits on calls and searches, which bound the worst case

Source: OpenRouter, Prompt Caching
