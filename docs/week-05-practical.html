Make the point that the queries were written before the data: that is the lecture's validation step, a question whose query cannot be written exposes a gap in the model. Every query is a single pattern.

Step 2 — Read the model

(:Document)-[:HAS_CHUNK]->(:Chunk)-[:NEXT]->(:Chunk)       text layer, no API call
(:Document)-[:FOR_WEEK]->(:Week)                          week read from the file name
(:Chunk)-[:MENTIONS]->(:Topic|Tool|Deliverable)           from extraction
(:Topic)-[:BUILDS_ON]->(:Topic)   (:Topic)-[:USES]->(:Tool)
(:Deliverable)-[:ASSESSES]->(:Topic)                      each with r.chunks
  1. Why is FOR_WEEK a relationship, but a document's kind a property?
  2. Why is the alias table written by reading the output, not by the model?
  3. Why does r.chunks list each chunk once?
7

≈7 min. Notebook Part 2. The model is in week5/kg_model.py, written once; the schema and the loader's check are built from it.

Answers. (1) Q1 and Q4 traverse from a document to its week; nothing traverses the kind, it is only read. (2) Which names are one entity is a judgement that must be the same on every run and checkable by a person; a model asked to merge names drifts between runs as much as the names do, and a wrong merge puts a false fact into the graph. (3) One relationship stated by three chunks would otherwise be three parallel relationships, and every path through it would be counted three times; and the list must not grow on a second load.

The chunk ids are <file>#<position>. Chunking is deterministic, so they are the same on every machine: checked 2026-10-04, re-chunking reproduces all 183 chunks Week 3 stored.

Step 4 — A schema the model must follow

class Message(BaseModel):
    category: Literal["setup", "concept", "deadline", "other"]
    urgent: bool
    summary: str

Literal becomes an enum: the model may return only those four.

Extraction's Mention.type is the same, read from kg_model.py: Literal[tuple(ENTITY_TYPES)] = Literal["Topic", "Tool", "Deliverable"].

10

≈7 min. Notebook Part 3, then the opening of Part 4. Two calls. Part 3 builds on the Week 2 practical's §5, where students replaced a polite request for JSON with schema=; here they read the JSON Schema the class produces, see result.parsed arrive as a typed object, and compare the same request made in the prompt alone.

Two measured points, 2026-10-04, gpt-5-nano via Lightning. First, do not promise that the prompt-only version fails: asking for the same JSON in the prompt parsed in six of six tries. The argument is the guarantee, not a demonstration: over 61 extraction calls one non-conforming reply is enough, and sent without strict mode this model returned "topic" for "Topic". Second, the schema fixes the shape and the vocabulary, not the judgement: the same message about a Docker port and a deadline was classified deadline in one run and setup in the next. This is the extraction lesson in miniature: a closed schema prevents undeclared types, not a wrong use of a declared one.

tuple() of a dictionary gives its keys, which is all the second line on the slide does. Read the instruction as well (instruction()): it asks for what a chunk states, not what is plausible, and defines each entity and relationship type in one line.

≈5 min. Notebook Part 5, Exercise 3. Both tables are in kg_model.py; read the comment above them. On the reference extraction (2026-10-04) resolution took 428 distinct (type, key) pairs to 388 entities: 46 entities had several spellings, mostly capitalisation, merged by the key alone; 10 names still came under two types and became two nodes; 10 relationships were dropped because an end had the wrong type, such as a Tool at the end of a BUILDS_ON.

A wrong merge puts a false fact into the graph; a missed one only leaves two nodes. That is why the resolver does nothing clever, and why the tables hold only certain entries. Step 12 shows a wrong merge the key made by itself.

The Ukrainian example is measured (2026-10-04, pymorphy3): «Іван Франко» gives іван франко, «Івана Франка» gives іван франк, read as the currency. It is for Lab 2; the course corpus is English.

Co-mention is not citation

A chunk that mentions two topics does not state the relationship between them.

MATCH (c:Chunk)-[:MENTIONS]->(a:Topic)-[r:BUILDS_ON]->(b:Topic)<-[:MENTIONS]-(c)
WHERE NOT c.id IN r.chunks
RETURN count(*)

Only the ids in r.chunks may be cited.
