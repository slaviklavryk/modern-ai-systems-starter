Modern AI Systems · Lecture 5

Week 5 — Knowledge graphs

1

≈90 min for the session. Run sheet: none. week-05-lecture-plan.md states each section's intent; the per-slide timings below are the schedule, and they sum to 86 minutes.

Organising principle, from the plan: Week 4 taught the database, and students reconstructed the design of the course graph in its practical without designing a graph themselves. This session is about design first. Sections 3 to 5 carry its weight; extraction, resolution, and the pipeline follow as consequences of design decisions. The course graph is the worked example throughout, because every one of its relationships was written by hand and none was extracted, so it shows the difference between a relationship that can only be trusted and one that can be cited.

No live demonstration and no API call in this session. Every output shown was recorded beforehand, with its provenance in the slide's notes.

If the session runs long, shorten section 8 to the load order and the warning about extraction time: the practical builds the pipeline in full.

What a graph captures that a vector does not

2

Section divider. Plan §1. ≈8 min.

The goal: students state the difference between the two representations in terms of what each asserts, and define a knowledge graph independently of the database that stores it.

Two representations, two kinds of claim

EmbeddingKnowledge graph
UnitA chunkA fact: two entities and a typed relationship
AssertsNothing about the world: only near in meaningAn explicit fact, stated once
SupportsRanking by similarityFollowing, counting, combining

A knowledge graph is the graph of a domain's entities and their explicit relationships, independent of the database that stores it.

3

≈3 min. The middle row is the point of the slide. An embedding places a chunk near other chunks and makes no claim; a relationship in a graph is a claim, and can be right or wrong.

The definition is deliberately independent of Neo4j. The term covers property graphs and the RDF graphs that Week 4 named and set aside.

The same knowledge, two ways

Vector retrieval returns a chunk:

"Albert Einstein worked on relativity."

A graph states facts, and can be traversed from any of them:

(:Person {name: 'Einstein'})-[:DEVELOPED]->(:Theory {name: 'Relativity'})
(:Person {name: 'Einstein'})-[:WORKED_AT]->(:Institution {name: 'Princeton'})
(:Person {name: 'Einstein'})-[:BORN_IN]->(:City {name: 'Ulm'})
4

≈3 min. The syllabus's example. Ask the class which question the graph answers that the chunk cannot: who developed a theory and worked at Princeton, for instance, or which theories were developed by people born in a given city. Each is a pattern over the facts; none is stated in a single chunk.

Two layers: the text and the domain

5

Section divider. Plan §2. ≈9 min.

The goal: students describe a graph built for retrieval as two layers joined by one relationship, and state what the join can and cannot do.

Two layers, one join

TEXT LAYER     (:Document)-[:HAS_CHUNK]->(:Chunk)-[:NEXT]->(:Chunk)
               built mechanically          |
                                      [:MENTIONS]
                                           v
DOMAIN LAYER          (:Topic)-[:BUILDS_ON]->(:Topic)<-[:COVERS]-(:Week)
designed                 the modelling work
6

≈4 min. This is the answer to the exercise that closed the Week 4 practical, in which students designed on paper what the course graph would need in order to answer which chunks discuss graph traversal.

The text layer requires no judgement: documents, their chunks, and the order of the chunks. The domain layer is the design. MENTIONS is the one relationship between them, and producing it is the extraction of section 6.

The label Chunk and its id key are those of week4/graph_vectors.py. The names Document, HAS_CHUNK, NEXT, and MENTIONS are the course's convention from this week; students may use their own if they use them consistently.

Designing the domain model from competency questions

7

Section divider. Plan §3. ≈14 min.

The goal: students derive a model from its questions, validate it before any data exists, and criticise a model that was not derived that way. This is the centre of the session.

Questions first

  1. Write the competency questions: multi-hop questions that vector retrieval cannot answer
  2. The nouns in their answers become entity types
  3. The connections between those nouns become relationship types
  4. Values that are only ever read become properties
  5. A relationship type that no question traverses is removed
8

≈3 min. Step 4 is Week 4's rule, section 3: a value that is only read is a property; anything traversed through or shared is a node.

On the term: competency questions come from ontology engineering, where a formal model is judged by whether it can answer them. An ontology is the formal version of a domain model: classes in hierarchies, properties with declared domains and ranges, and rules from which facts are inferred, usually in RDF and OWL. Name it so that students recognise it. The course does not use one: the students' graphs are small, private, and designed for retrieval, and a second data model would cost more than it returns at that scale.

A model is validated before any data exists

Every competency question must have a Cypher query on the model.

"Which Week 3 topics must I know before Lab 2?"

MATCH (:Deliverable {name: 'Lab 2'})-[:ASSESSES]->(:Topic)
      -[:BUILDS_ON]->{1,4}(t:Topic)<-[:COVERS]-(:Week {number: 3})
RETURN DISTINCT t.name

A question whose query cannot be written exposes a gap in the model.

9

≈4 min. Read the pattern aloud: a deliverable assesses a topic, which builds on, through one to four hops, a topic covered in Week 3. Each relationship type in the pattern is one that this question justifies.

The query is written against the course graph's actual model, course_graph.cypher: ASSESSES, BUILDS_ON, and COVERS. It is not run in the lecture; the practical asks students to write this kind of query for each of their own questions before extracting anything.

Students already did the reverse in the Week 4 practical, section 8: for each relationship type of the finished graph, the question it exists to answer. Today the method runs forwards.

Graph design defects

DefectExample
Decorative relationshipA type that no competency question traverses
Generic relationshipRELATED_TO: connected, but not stated how
Over-general entity typeThing, Concept: a traversal from it reaches everything
A value as a node(:Year {value: 2024}), although the year is only read
A missing relationshipA question whose query cannot be written
10

≈4 min. These are exactly the five checks of the practical's model review, section 3, where students review each other's models in pairs.

Lab 2's descriptors (syllabus §9): Excellent, relationships reflect the domain's actual structure and enable multi-hop questions vector search cannot answer; Good, sound but mostly shallow or decorative.

Ask students to test the entities and relationship types of their approved proposals against this table before the practical.

Direction and granularity

Direction is a naming convention:

  • (:Topic)-[:BUILDS_ON]->(:Topic)
  • (:Topic)-[:IS_BUILT_ON]->(:Topic)

Granularity is set by the questions, not by the domain.

  • A distinction no question uses belongs in a property or a second label, not a new type

Not: (:LectureTopic) (:PracticalTopic) two types, so every query names both Instead: (:Topic {session: 'practical'}) a property, if it is only read or: (:Topic:Practical) a second label, if queries filter on it ``

11

≈3 min. Direction: Week 4 showed that a pattern can follow a relationship against its stored direction at no cost. Storing the inverse as well doubles the relationships and creates two facts that can disagree.

Granularity: a domain always offers finer distinctions than the questions need. A course could distinguish lecture topics from practical topics; unless a question asks which, that distinction is a property, or a second label on the same node.

Where relationships come from

12

Section divider. Plan §5. ≈10 min.

The goal: for every relationship, students state how it came to be there, how that is recorded, and why it matters for an answer built on it.

Three origins

OriginExampleAn answer built on it can
CuratedWritten by a personOnly be trusted
DerivedFrom a table or a metadata fieldInherit its source's authority
ExtractedRead from a chunk that states itCite the chunk

An extracted relationship extends Week 3's grounding to the graph.

13

≈3 min. The three also differ in cost and coverage. Curated is cheap for a small model and impossible at scale; derived is free where the structured data exists; extracted costs generation quota and has the failure modes of section 6.

Students choose an origin for each relationship type of their own model. That choice determines how much of section 6 they need.

The course graph is curated

Every one of its 141 relationships was written by hand, from the syllabus.

(:Topic {name: 'Chunking'})-[:BUILDS_ON]->(:Topic {name: 'Embeddings'})

Most BUILDS_ON relationships are editorial judgements that no chunk of the course material states. An answer built on them cannot cite a source.

14

≈2 min. This answers the question left open in section 1: who wrote the relationships that answered Week 4's question. The answer the model gave was correct and cited the graph's facts, but the facts themselves rest on the author's judgement.

This is not a defect of the course graph, which was built to teach Cypher. It is the property that makes it a useful contrast with the students' graphs.

Extracting entities and relationships with a model

15

Section divider. Plan §6. ≈17 min.

The goal: students extract with structured output constrained to their declared model, and name the ways extraction fails. All outputs in this section were recorded beforehand.

Extraction: chunks in, facts out

IN     [w3-plan-3]  "...Students should also recognise 'cosine distance', reported
                     by some vector stores as one minus the similarity..."
       [w3-plan-5]  "...why an entire document cannot be embedded as one vector..."

                     model  +  instruction  +  schema
                                    |
                                    v
OUT    entities:   Cosine similarity, Cosine distance, Chunking, ...   (all Topic)
       relations:  Cosine distance -[:BUILDS_ON]-> Cosine similarity   from w3-plan-3

Each chunk goes in with an id. Each relationship comes back with the id of the chunk that stated it.

16

≈2 min. Explain the task before showing any code. The input is several chunks in one call, each prefixed with its id. The output is not prose: it is two lists, the entities found and the relationships between them, in the types the design declares.

The output shown is abridged from the first recorded run (2026-10-04, course graph model Topic and BUILDS_ON). The full result of both runs is on the slide after next. The two chunks were sections 3 and 5 of the Week 3 lecture plan, sent whole: they are larger than the chunks week3/chunking.py produces, and w3-plan-3 and w3-plan-5 are ids assigned for the run, not stored chunk ids.

The chunk id on each relationship is the provenance of section 5: it is what lets an answer built on this relationship cite its chunk.

Why the schema comes before extraction

Some tools extract without a schema and let the types emerge from the text.

The result: relationship types for which no question was written.

That is the decorative model, produced automatically.

17

≈2 min. Students will meet schema-free extraction in tools and tutorials, including the community-summarisation approaches to graph indexing that Week 6 mentions. It has a place for exploring an unfamiliar corpus. For a graph designed to answer known questions, the design comes first and constrains the extraction.

What an ontology is

What it givesExample
Taxonomycategories and subcategories: a hierarchyFoodstuffs → Fruit → Apple
Ontologythe meaning of each type, how types relate, and rulesOrder CONTAINS Product
Knowledge graphthe instances themselves, connectedthis order contains this apple

"The knowledge graph is what you build, while taxonomies and ontologies are the blueprints."

18

≈3 min. The definitions and the e-commerce examples follow John Stegeman, "Taxonomy vs. ontology vs. knowledge graph", Neo4j blog, 16 June 2026 (https://neo4j.com/blog/knowledge-graph/taxonomy-vs-ontology-vs-knowledge-graph/). Its definition of an ontology, to read aloud: "An ontology describes a domain by providing semantic meanings and logical rules. It provides a model of the important aspects of that domain and how they relate." The quotation on the slide is from the same article.

Make the three layers concrete with the course. The knowledge graph is what the practical builds: this chunk mentions Chroma, this topic uses Chroma. The ontology is the schema of the previous slide, written in kg_model.py: three entity types, and three relationship types each with a declared direction, BUILDS_ON from a Topic to a Topic, USES from a Topic to a Tool, ASSESSES from a Deliverable to a Topic. It is enforced: the loader drops a relationship whose end has the wrong type. The course graph has no taxonomy; a hierarchy such as cosine distance being a kind of similarity measure would need an IS_A relationship, which no competency question asks for.

What separates this from an ontology in the formal sense is what it leaves out: class hierarchies, rules from which new facts are inferred (BUILDS_ON being transitive, say), and a standard language, usually RDF and OWL. This connects to the term on the competency-questions slide: those questions come from ontology engineering. The course stops at the small version, for the reason given there: the students' graphs are small, private, and designed for retrieval.

Entity resolution

19

Section divider. Plan §7. ≈8 min.

The goal: students explain why extraction produces duplicate entities and choose a canonical key that merges them.

The same entity, different strings

From the two recorded runs, on identical input:

Run 1Run 2
Chunkingcorpus chunking
Cosine similaritycosine similarity

MERGE compares keys exactly. Embeddings compared meaning; a key does not.

20

≈2 min. In Week 3 this problem did not arise, because two chunks that use different words for the same thing still embed close together. A key on which MERGE matches is compared character by character, so the problem returns with the graph.

Lower-casing merges the second row. Nothing mechanical merges the first.

Two remedies apply together: the instruction asks for each name in a canonical form, and the loader reduces each name to a normalised key. For a corpus whose entities are already known, passing the list of existing names to the model is a third.

What normalisation cannot do

Normalisation merges forms of one name. It does not merge different names for one entity: ЛНУ and Львівський національний університет.

  • A curated list of aliases, applied by the loader
  • Or a known defect, recorded as such

Choosing the key is part of designing each entity type.

21

≈2 min. Connect this to Week 4's idempotent loading: MERGE on a key makes a load repeatable only if the key identifies the entity. Resolution is what gives the key its meaning.

From the design to a re-seedable ingest.py

22

Section divider. Plan §8. ≈8 min. The first section to shorten if the session runs long: reduce it to the load order and the warning on the last slide.

Where the design is enforced

Neo4j Community enforces only uniqueness constraints. The design lives in code, in three places that must agree:

  1. The uniqueness constraints, one per entity key
  2. The extraction schema, with its declared types
  3. The loader, which refuses an undeclared relationship type
23

≈2 min. Week 4, section 2: Neo4j imposes no schema by default, and existence, type, and key constraints are Enterprise features. A model that is written down in three places can drift; the practical writes the declared types once and builds the schema and the loader's check from that list.

The load order

  1. Constraints
  2. The text layer: documents and chunks
  3. Entities, merged on their keys
  4. Relationships between entities
  5. MENTIONS, from chunks to entities

Nodes before relationships, at every stage. Run it twice; the counts do not change.

24

≈2 min. This is Week 4's rule for idempotent loading, section 6, applied to two layers: merge each node on its key first, and merge relationships between nodes that already exist. Merging a whole pattern creates duplicates, or with constraints an error.

The practical, section 5, loads a sample in this order and runs the load twice.

Four stages, two of them saved

documents ──► chunks ──► embeddings ──► extraction ──► load ──► Neo4j
             free        API quota       API quota      free
             determ.     saved to file   saved to file  idempotent

Rebuild re-runs the load from saved results, in seconds. Re-extraction is a separate, deliberate step.

25

≈3 min. The syllabus makes a re-seedable ingest.py mandatory from this week: it protects against a deleted volume and a changed machine, and it is the reproducibility practice the course teaches.

The syllabus asks for a script that rebuilds the graph from source data in one command. The plan reads source data as the documents together with the saved embeddings and extraction results, because repeating extraction on every rebuild at six requests per minute is not a rebuild. This reading is recorded in the plan's notes for the syllabus.
