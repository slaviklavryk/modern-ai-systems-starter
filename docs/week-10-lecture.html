MCP: a standard protocol for tools

Modern AI Systems · Lecture 10

Week 10 — A tool written once, used by any application

1

Main idea

In Weeks 8 and 9 every tool lived inside the agent that used it.

Today a tool is separated from the application:

  • the tool is offered by a server
  • any application can use it through one protocol
  • the model's side of a tool call does not change

MCP standardises the application's side.

2

A tool belongs to one agent

In Week 9 the course tools are Python functions in agent_stack.py, passed to create_agent in the notebook.

Another application that needs search_course:

  • a chat application
  • a code editor
  • another team's agent, written in another language

must define the tool again, in its own format, and run it in its own process.

3

MCP

The Model Context Protocol: an open protocol between AI applications and the tools and data they use.

  • Current specification: the revision dated 28 July 2026
  • Created by Anthropic; since December 2025 maintained by the Agentic AI Foundation, a fund under the Linux Foundation co-founded by Anthropic, Block and OpenAI

A vendor-neutral standard, not one vendor's plugin format.

4

Three roles

RoleWhat it isWhat it does
Hostthe AI application: a chat application, a code editor, our agentholds the model and the conversation; decides what reaches the model; asks for the user's consent
Clienta connector inside the hosttalks to exactly one server
Servera program that offers capabilitiesruns on the same machine or across a network

The model is not a party to the protocol. Only the host calls it.

7

What MCP server offers: tools

A server offers three kinds of capability, told apart by who decides to use each. The first is Week 8's.

A tool is a function that the server runs on request, with the arguments it is given.

  • Who decides to use it: the model, during the loop: which tool, when, and with what arguments
  • What it does: reads, as exchange_rate and search_course do, or writes, as remember does
  • What comes back: a result, which the host returns to the model as an observation

The specification calls tools model-controlled. The host still decides which tools the model is shown, and may ask the user before a call runs.

8

What MCP server offers: resources

A resource is data that the server offers for reading, identified by a URI: a document, a file, a database's schema.

  • Who decides to use it: the application, which lists resources for the user to choose or attaches them itself
  • What it does: nothing; a resource supplies data and takes no action
  • What comes back: its contents, as text or binary data, with a MIME type
host ──► server    resources/list    the server names  course://graph/schema
host ──► server    resources/read    course://graph/schema
host ◄── server    the graph's node labels, relationship types and properties
host ──► model     the schema, placed in the instruction by the host

Week 6's text-to-Cypher placed the graph's schema in its instruction in the same way: the application chose it, and the model never asked for it.

9

What MCP server offers: prompts

A prompt is a template of messages that the server defines, with named arguments.

  • Who decides to use it: the user, who selects it from a command in the interface, such as a slash command
  • What it does: nothing by itself; it supplies the opening of a conversation
  • What comes back: messages with the arguments filled in, which the host places in the conversation
user               selects /explain_topic, topic = "chunking"
host ──► server    prompts/get   explain_topic {"topic": "chunking"}
host ◄── server    user: "Explain chunking from the course materials, citing each source."
host ──► model     that message, as the user's turn

The server writes the text; the user decides when it is used. To sort the capabilities of your own project, ask who decides to use each.

11

One tool call, over MCP

host ──► model     the question + the tool definitions, obtained with tools/list
host ◄── model     a tool call:   exchange_rate {"currency": "EUR"}
host ──► server    tools/call     exchange_rate {"currency": "EUR"}
host ◄── server    the result:    "1 EUR = 50.5766 UAH, set by the NBU for 26.10.2026"
host ──► model     the messages + the tool's result
host ◄── model     the answer

The lines with the model are Week 8's. Only the two lines with the server are new: the function runs in another program.

The tools are divided by subject. The exchange rate reads the NBU's public API; the course tools share the graph and the embeddings. Each server is written, run and changed on its own, and a host connects only to the servers it needs.

The functions are those of Week 9, written once. The agent becomes one host among several, with one client per server, and obtains its tools from the servers instead of defining them.

14

Inspecting a server: MCP Inspector

MCP Inspector is the MCP project's developer tool for servers: a host with no model, in which every request is made by hand.

npx @modelcontextprotocol/inspector --config servers.json

It runs on Node.js and opens in the browser; servers.json names each server and its address.

TabShowsRequests
Toolseach definition, and a form to call the tooltools/list, tools/call
Resourcesthe resources, and the contents of oneresources/list, resources/read
Promptsthe prompts, and one filled with argumentsprompts/list, prompts/get
Protocolevery message, client → server and server → clientall of them

The server answers the Inspector as it answers the agent: what the Inspector shows is what every host receives.
