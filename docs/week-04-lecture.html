Why a graph database

2

A trade-off, not a replacement

StoreAnswers wellAnswers badly
Vector indexWhat is similar to this?How is this connected to that?
RelationalWhich rows match? Aggregates, reportsConnections of unknown depth
GraphHow is this connected to that, however far?Aggregate, tabular workloads

A graph database stores each relationship as a record that points at the two nodes it joins. Following it needs no join.

4

≈2 min. State the last row's second column explicitly: a graph database is the wrong tool for a monthly sales report, and the course does not claim otherwise. Each store is used for what it does well.

The mechanism in one sentence: a relationship is a stored record that refers directly to its two nodes, so following it is a lookup rather than a join computed at query time.

The property graph model

5

Section divider. Plan §2. ≈10 min.

The goal: students describe the model precisely and distinguish it from the mathematical graph they already know. Do not re-teach graph theory.

Today's graph: films and the people who made them

Neo4j's standard Movies graph.

  • 38 Movie nodes and 133 Person nodes
  • 253 relationships: ACTED_IN, DIRECTED, PRODUCED, WROTE, REVIEWED, FOLLOWS

The dataset of Neo4j's own documentation and Browser guide. You will find many more examples of it.

6

≈2 min. Measured 2026-09-27 on the pinned Neo4j 5.26: 171 nodes and 253 relationships, of which 172 are ACTED_IN, 44 DIRECTED, 15 PRODUCED, 10 WROTE, 9 REVIEWED and 3 FOLLOWS.

Students load it in the practical with python load_graph.py --movies, or with :play movies in Neo4j Browser, which runs the same script.

State the one caveat now rather than in the practical: because this graph is so widely published, an AI assistant will write any standard query about it instantly. The exercises teach only if the query is written before the assistant is asked.

Nodes, relationships, properties

  (:Person {name: 'Keanu Reeves', born: 1964})
                    |
                    |  [:ACTED_IN {roles: ['Neo']}]
                    v
  (:Movie {title: 'The Matrix', released: 1999})
  • A node carries zero or more labels: Person, Movie
  • A relationship has exactly one type, one direction, and exactly two nodes
  • Properties are key–value pairs, on nodes and on relationships
7

≈3 min. Read the diagram aloud, node, relationship, node. The two things students who know only relational tables tend to miss are on this slide: a relationship is a thing in its own right, with a type and properties, and a node's label is closer to a tag than to a table, since one node may carry several.

The roles property sits on the relationship. Section 3 returns to why.

What is new relative to graph theory

A mathematical graph is vertices and edges. A property graph adds four things:

  1. Labels on nodes
  2. Types on relationships
  3. Properties on both
  4. Relationships as stored records, not an adjacency to be computed

Direction is always stored, and may be ignored when querying.

8

≈2 min. These four additions are the whole of what is new. Do not define a graph.

The direction point is practical: because a query can follow a relationship in either direction, the direction chosen when modelling is a convention for readability, not a restriction on what can be asked. (:Person)-[:ACTED_IN]->(:Movie) can be matched from the film's side as easily as from the actor's.

No schema by default

Any node may carry any property. Neo4j checks nothing unless it is told to.

  • Convenient while a model is being designed
  • A source of silent inconsistency once data arrives from several places: name on one node, Name on another, and no error

Constraints add the schema back. Section 6 shows how.

9

≈2 min. Schema-optional is a design choice, not an omission. It suits exploratory modelling, which is what Week 5 asks students to do with their own domains, and it becomes a liability when a loader, a model, and a person all write to the same graph.

Modelling: node, relationship, or property

10

Section divider. Plan §3. ≈7 min. The first section to shorten if the session is running long.

From tables to a graph

Relational schemaProperty graph
A row of personA Person node
A foreign keyA relationship
A join table acted_in(person_id, movie_id, roles)An ACTED_IN relationship
A column of the join table (roles)A property of the relationship

The role Keanu Reeves played belongs to neither the person nor the film. It belongs to the fact that one acted in the other.

11

≈3 min. Start from what students know. Every row of this table is a translation they can perform mechanically on a schema they have designed before.

The last row is the one to dwell on. In the relational schema, roles could only live in the join table, because it describes the pairing. The property graph has the same place for it: the relationship.

One fact, two models

Director as a property:      (:Movie {title: 'Unforgiven', director: 'Clint Eastwood'})

Director as a relationship:  (:Person {name: 'Clint Eastwood'})-[:DIRECTED]->(:Movie {title: 'Unforgiven'})

Who acted in a film they also directed? The second model answers with a pattern:

MATCH (p:Person)-[:ACTED_IN]->(m:Movie)<-[:DIRECTED]-(p)
RETURN p.name, m.title

A value that is only read is a property. Anything traversed through or shared is a node.

12

≈4 min. The heuristic, then the reason for it. With the director stored as a string, the question needs a comparison between a person's name and a film's property, which breaks on the first spelling variation and cannot follow the director anywhere else. With the director as a node, the question is a pattern in which the same variable p appears twice.

On the Movies graph this query returns Tom Hanks (That Thing You Do), Clint Eastwood (Unforgiven), and Danny DeVito (Hoffa). It is exercise 2 in the practical, so show the query but not the result.

State the general lesson: a graph model is designed backwards from the questions it must answer. This is the Lab 2 criterion that asks whether relationships reflect the domain's structure or are merely decorative.

Cypher: querying by pattern

13

Section divider. Plan §4. ≈15 min, most of it live in Neo4j Browser on the Movies graph.

A query is a pattern

   (p:Person)  -[:ACTED_IN]->  (m:Movie)
    a node       a relationship     a node
   ( ) round      [ ] square        arrow = direction

MATCH asks the database for every place this pattern occurs.

Declarative, like SQL: you describe what to find, not how to find it.

14

≈3 min. The notation is visual on purpose: parentheses look like nodes, the arrow looks like the relationship. Students who read the pattern aloud as a sentence, "a person who acted in a movie", are reading it correctly.

Make the SQL comparison explicit: neither language states the order in which the database should do the work. The planner decides.

MATCH, WHERE, RETURN

MATCH (p:Person {name: 'Tom Hanks'})-[:ACTED_IN]->(m:Movie)
WHERE m.released >= 2000
RETURN m.title, m.released
ORDER BY m.released
SELECT m.title, m.released
FROM person p JOIN acted_in a ON a.person_id = p.id
              JOIN movie m    ON m.id = a.movie_id
WHERE p.name = 'Tom Hanks' AND m.released >= 2000
ORDER BY m.released;
15

≈3 min. Run the Cypher live in Browser. Result on the Movies graph: Cast Away (2000), The Polar Express (2004), The Da Vinci Code (2006), Charlie Wilson's War (2007), Cloud Atlas (2012).

Point at the two joins in the SQL and the one arrow in the Cypher. The join table acted_in has become the relationship, exactly as section 3 said.

Two relationships, one pattern

MATCH (:Person {name: 'Keanu Reeves'})-[:ACTED_IN]->(m:Movie)<-[:DIRECTED]-(d:Person)
RETURN DISTINCT d.name AS director
ORDER BY director

A pattern can be any shape. The arrows point in the direction stored, and the pattern reads left to right regardless.

16

≈2 min. Run live. Six directors: Howard Deutch, Lana Wachowski, Lilly Wachowski, Nancy Meyers, Robert Longo, Taylor Hackford.

Ask why DISTINCT is needed. The Wachowskis directed three Matrix films, so without it each appears once per film.

Aggregation

MATCH (p:Person)-[:ACTED_IN]->(m:Movie)
RETURN p.name AS actor, count(m) AS films          // Tom Hanks 12, Keanu Reeves 7, ...
MATCH (p:Person)-[:ACTED_IN]->(m:Movie)
RETURN p.name AS actor, m.title AS title, count(m) AS films     // every count is 1

Every non-aggregated expression in RETURN is part of the grouping key.

17

≈3 min. Show the first, then add the one column and run it again. Ask the class why every count became 1 before explaining it.

The explanation: Cypher has no GROUP BY clause. It groups by whatever non-aggregated expressions appear beside the aggregate, so adding m.title made each group a single actor–film pair. This is the point at which readers fluent in SQL most often misread a query, which is why the practical includes it.

Measured on the Movies graph: Tom Hanks 12 films, Keanu Reeves 7, then Hugo Weaving, Jack Nicholson, and Meg Ryan with 5 each.

WITH: one query, several stages

MATCH (p:Person)-[:ACTED_IN]->(m:Movie)
WITH p, count(m) AS films
WHERE films >= 5
RETURN p.name AS actor, films

WITH passes rows to the next stage. Filtering on an aggregate is what SQL's HAVING does.

18

≈2 min. WITH is the clause that turns a single pattern into a pipeline. Students will need it in Week 6, where queries combine a search, a traversal, and an aggregation.

Result: the five actors from the previous slide.

OPTIONAL MATCH: the outer join

MATCH (p:Person)
OPTIONAL MATCH (p)-[:ACTED_IN]->(m:Movie)
WITH p, count(m) AS films
WHERE films = 0
RETURN p.name AS person

People in the graph who never acted: directors, producers, writers, reviewers.

19

≈1 min. With a plain MATCH, a person with no ACTED_IN relationship would simply not appear, which is an inner join. OPTIONAL MATCH keeps them, with m null, which is a left outer join. On the Movies graph the query returns 31 people.

Neo4j Browser draws a picture. A program receives a table.

Traversal: paths of unknown length

21

Section divider. Plan §5. ≈12 min, live in Browser.

The capability that justifies a graph database. Do not compare it with vector retrieval; that is Week 6's demonstration.

How is Kevin Bacon connected to Meg Ryan?

MATCH p = SHORTEST 1 (:Person {name: 'Kevin Bacon'})-[]-+(:Person {name: 'Meg Ryan'})
RETURN [n IN nodes(p) | coalesce(n.name, n.title)] AS route
Kevin Bacon → A Few Good Men → Rob Reiner → When Harry Met Sally → Meg Ryan

No record in the graph states this connection. The traversal assembles it.

22

≈3 min. Run live. Four hops, through a film, its director, and another of his films.

This is the Week 3 failure class on the Movies graph: the answer lies in how facts are connected, not in any one of them. -[]-+ means any relationship, either direction, one or more times.

If time allows, show the Bacon-number distribution, which is also in the practical: following ACTED_IN only, 19 people are one film away from Kevin Bacon, 53 two, 20 three, and 9 four.

Two syntaxes you will meet

This course teaches (GQL standard)You will also see (older Cypher)
-[:ACTED_IN]-{1,6}-[:ACTED_IN*1..6]-
SHORTEST 1 (a)-[]-+(b)shortestPath((a)-[*]-(b))

Both run on the course's Neo4j 5.26. Read the Cypher 5 manual.

23

≈2 min. Verified 2026-09-27 against the Cypher 5 manual: quantified path patterns arrived in 5.9 and SHORTEST in 5.21, both conform to GQL, and the older forms remain supported but do not.

Separately, and more important: most of Neo4j's current online documentation, and much of what an AI assistant writes, is Cypher 25, which does not run on 5.26. Direct students to https://neo4j.com/docs/cypher-manual/5/introduction/ and tell them that a syntax error on a copied query is most likely a version mismatch.

Why the depth is always bounded

Paths from Keanu Reeves, any relationship, either direction:

Hops123456
Paths7381118282,93821,142

A graph of 171 nodes. Six hops already means tens of thousands of paths.

24

≈2 min. Measured 2026-09-27 on the pinned Neo4j 5.26 with MATCH p = (:Person {name: 'Keanu Reeves'})-[]-{1,6}(x) RETURN length(p), count(*).

The rule: always state an upper bound. An unbounded pattern on a large, densely connected graph enumerates paths it can never finish listing.

Writing to the graph idempotently

25

Section divider. Plan §6. ≈9 min, live in Browser.

The section that matters most for the rest of the course: from Week 5, every student's graph must be rebuildable by a re-seedable ingest.py.

CREATE adds; MERGE finds or creates

CREATE (p:Person {name: 'Keanu Reeves'})       // always adds a node, even a duplicate

MERGE (p:Person {name: 'Keanu Reeves'})        // finds it, or creates it if absent
ON CREATE SET p.born = 1964

Idempotent: running the load twice produces the same graph.

26

≈2 min. The MERGE line is taken from Neo4j's own Movies script, which is written this way throughout. Measured: loading it twice leaves 171 nodes and 253 relationships unchanged.

ON CREATE SET runs only when MERGE creates the node; SET on its own runs every time. Name DETACH DELETE here as well, the operation that removes a node together with its relationships.

The standard mistake

// WRONG: merges the whole pattern. If the relationship is missing,
// MERGE creates all of it, including two new copies of existing nodes.
MERGE (:Person {name: 'Tom Hanks'})-[:ACTED_IN]->(:Movie {title: 'The Matrix'})
// RIGHT: merge each node on its key, then only the relationship.
MERGE (p:Person {name: 'Tom Hanks'})
MERGE (m:Movie {title: 'The Matrix'})
MERGE (p)-[:ACTED_IN]->(m)
27

≈3 min. The single most common error in Cypher loading scripts. MERGE matches or creates the entire pattern as one unit. It does not look up the two nodes separately.

Demonstrate the wrong form on a throwaway label with no constraint: it produces two copies of each node. The practical repeats this. The next slide shows what happens on the real, constrained labels.

A constraint turns a silent error into a loud one

CREATE CONSTRAINT person_name IF NOT EXISTS
FOR (p:Person) REQUIRE p.name IS UNIQUE

The wrong MERGE, run against constrained labels:

ConstraintValidationFailed: Node(68) already exists with label `Person`
and property `name` = 'Tom Hanks'

The constraint also gives MERGE an index to find the node by.

28

≈2 min. Measured on the pinned 5.26: the Movies graph's own constraints turn the wrong MERGE into this error, and nothing is written.

This is the schema that section 2 said Neo4j does not impose by default. Community edition supports uniqueness constraints only; existence, type and key constraints are Enterprise features. Do not present them as available.

Neo4j from Python

29

Section divider. Plan §7. ≈6 min.

The driver, directly

from neo4j import GraphDatabase

driver = GraphDatabase.driver("bolt://localhost:7687", auth=("neo4j", "modernai"))
records, summary, keys = driver.execute_query(
    "MATCH (m:Movie {title: $title})<-[:ACTED_IN]-(p:Person) RETURN p.name AS actor",
    title="The Matrix",
)

The official driver, with no framework over it. $title is a parameter.

30

≈2 min. The course policy from syllabus §4: build the mechanism before adopting an abstraction over it. week4/graph_db.py is a few lines around exactly this call, and the practical shows the call on its own.

The password is the local development one from the compose file. It is never to be reused.

Why every value is a parameter

title = "One Flew Over the Cuckoo's Nest"
query = "MATCH (m:Movie {title: '" + title + "'}) RETURN m"   # pasted into the text
CypherSyntaxError: Invalid input 's': expected an expression, ',' or '}'

The apostrophe broke the query. A value chosen by an attacker could change it. The parameterised version returns the cast.

31

≈3 min. The title is in the Movies graph, so the failure is not contrived. Measured on the pinned 5.26: concatenation raises this syntax error; the parameterised query returns Danny DeVito and Jack Nicholson.

The risk grows later in the course. From Week 5, some values reaching a query will have been written by a model, in LLM-assisted extraction, and in Week 7 untrusted text reaches tools. Parameters are also the route by which a query vector reaches the database in section 8.

The vector index: finding the way in

32

Section divider. Plan §8. ≈15 min, the last part of the demonstration, run from Python.

The section that connects the database to Week 3. It stops at the returned rows.

Switch graphs here, while introducing the section: python load_graph.py, which removes the Movies graph, then python graph_vectors.py, which embeds the 39 topic descriptions again, because their vectors were removed with the course graph. This is the one live embedding call in the session. If it returns 503, retry once and then show the recorded output.

A traversal needs a starting point

Every traversal so far began at a node named in the query: 'Keanu Reeves', 'Kevin Bacon'.

A user's question names none.

The vector index finds the starting nodes by meaning. The relationships supply what similarity could not.

33

≈2 min. This is the observation the whole session has been building towards. State it slowly.

One query now does two things in sequence: the Week 3 retrieval, to find where to start, and the section 5 traversal, to follow the relationships from there.

Vectors on nodes, an index over them

CREATE VECTOR INDEX topic_embeddings IF NOT EXISTS
FOR (t:Topic) ON t.embedding
OPTIONS {indexConfig: {`vector.dimensions`: 3072,
                       `vector.similarity_function`: 'cosine'}}
CALL db.index.vector.queryNodes('topic_embeddings', 3, $question_vector)
YIELD node, score

Vectors from Week 3's embedding client: document type for topics, query type for questions.

34

≈3 min. Nothing here is new machinery. The index is the approximate nearest-neighbour structure (HNSW) that Week 3 said most vector stores share, and vector.dimensions must equal the embedding model's output, 3072 for the course's pinned model.

Measured on the pinned 5.26: a vector of the wrong length is stored without any error and then silently left out of every search. week4/graph_vectors.py checks the length before writing for that reason.

db.index.vector.queryNodes is the only query interface on 5.26. Current Neo4j releases deprecate it in favour of a SEARCH clause, which belongs to Cypher 25 and does not run here. Students will find SEARCH in current documentation.

Search, then traverse

CALL db.index.vector.queryNodes('topic_embeddings', 1, $q) YIELD node AS topic, score
MATCH (topic)-[:BUILDS_ON]->{1,4}(first:Topic)<-[:COVERS]-(w:Week)
RETURN topic.name, collect(DISTINCT first.name + ' (week ' + w.number + ')')
