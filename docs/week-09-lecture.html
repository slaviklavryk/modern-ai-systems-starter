Main idea

Weeks 1–8 built the parts of an AI system one at a time. Today they are put together.

For each part:

  • where it sits in the stack
  • which part of the context it writes
  • whether it is fixed in code or decided by the model

Nothing new is introduced.

The context, filled in

SYSTEM      role, rules, "not stated"       written once, by you    Weeks 2–3
EXAMPLES    demonstrations                  written once, by you    Week 2
TOOLS       name, description, parameters   written once, by you    Week 8

SOURCES     passages and graph facts        a retriever             Weeks 3–6
QUESTION    what the user asked             the user

Every component, however it is built, ends as text in the context of one model call. This is context engineering.

When retrieval is a tool, its sources arrive in the history, as a tool's result.

Knowledge: two paths

ONCE, when the corpus changes
  documents ──► chunk ──► embed ──► store: Chroma, or Neo4j's vector index    Weeks 3–4
  chunks ──► model extracts entities and relationships ──► resolve ──► graph  Week 5

ON EVERY QUESTION
  question ──► retriever ──► numbered sources ──► grounded instruction ──► answer

The answering step is the same for every retriever (Week 6).

A follow-up question, in two places

Week 7   history + "How do we change it?"
           ──► the model rewrites it ──► retrieve ──► answer

Week 8   history + "How do we change it?"
           ──► the model calls search_course {"query": "change the distance metric in Chroma"}
           ──► the result ──► answer

The same decision: what to search for. In Week 7 a fixed step asks the model for it; in Week 8 the model makes it inside the loop.

Either way it can be wrong silently: log the query.

From a single call to an agent

a single call       prompt ──► answer                                   Week 2
a fixed pipeline    question ──► retrieve ──► answer                    Week 3
one model decision  question ──► router ──► one retriever ──► answer    Week 6
                    follow-up ──► rewrite ──► retrieve ──► answer       Week 7
an agent            question ──► model ⇄ tools ... ──► answer           Week 8

Down the list: more kinds of question handled, and more model calls, more paths through the system, and more ways to fail.

13

Use the most fixed arrangement that works

Each decision given to the model:

  • costs a model call, against the provider's request limits
  • adds a path: each run may differ, so testing covers runs, not steps
  • can be wrong silently, so its choices must be logged

Give a decision to the model when the right step cannot be known in advance: when it depends on what the previous step returned.

Use the leftmost architecture that solves the problem.

LangChain middleware: control over the loop

Middleware runs before and after each model call and each tool call. It is passed to create_agent as a list.

MiddlewareDoes
ModelCallLimitMiddlewarestops a run after n model calls
ToolCallLimitMiddlewarelimits the calls of one tool
ToolErrorMiddlewarereturns a tool's exception to the model
ModelRetryMiddlewareretries a failed model call
SummarizationMiddlewaresummarises older messages as the history grows
ContextEditingMiddlewareremoves old tool results from the context
HumanInTheLoopMiddlewarepauses before a tool call for a person to approve
LLMToolSelectorMiddlewarea model chooses the relevant tools first

Your own middleware: @dynamic_prompt builds the system prompt on every call, for example with recalled memory.
